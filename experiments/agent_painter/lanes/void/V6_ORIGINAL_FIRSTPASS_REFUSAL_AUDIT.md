## Interpretation and future testing

Untuned VOID repeats QA/tutorial prose, sometimes properly EOS-terminating; EOS alone is not instruction following. The first adapted candidate imitates JSON but regularly fails parsing. By 120 steps, EOS is reliable on this six-request sample, but duplicate JSON keys, unsupported Greeble details, invalid architectural fields and insufficient pipe topology remain. Do not conflate parser acceptance, compiler acceptance, native material ACK and request-conforming geometry.

**Controlled comparison caveat:** step16 ran with a 768-token generation cap and step120 with 1024; even the untuned EOS count changes. These archival comparisons cannot isolate the causal effect of update count. A future matched fresh/continued A/B must freeze prompt set, max-new-tokens, model and full data/numerical contracts.

The next useful learning input is structurally novel, globally split-reviewed, **positively native-admitted** TRAIN data, especially independent loop/multibranch connected constant-diameter pipes, recognisable Greeble mechanisms and genuinely different orthographic layouts, together with a single frozen 60-request/five-formulation DEVELOPMENT suite. No more unchanged-six-structure optimization should be launched. Shared source, peer PRs and compiler/native contracts remain untouched.

The new lane-only raw refusal verifier, its adversarial checks and a hosted read-only original-archive audit are separate source and run evidence; this document's original numbers were recomputed before those newer workflow results existed.
