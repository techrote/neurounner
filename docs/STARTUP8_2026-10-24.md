Runner class: GitHub-hosted `ubuntu-24.04`, four logical CPUs.

## Purpose

Request eight standard runners concurrently, place at least one model on each, and test whether the newly added runner-hosted candidates can:

1. download from their pinned source;
2. pass SHA-256 verification;
3. load under the pinned llama.cpp prebuilt;
4. reach the local health endpoint;
5. complete a short OpenAI-compatible chat inference.

All eight requested primary jobs entered the running state concurrently. Seven passed end-to-end in the first matrix. Qwen2.5-Omni-7B exposed a stale/incorrect SHA-256 registry entry at the download gate; the registry was corrected and a targeted retry then passed end-to-end.

## Observed host diversity

The simultaneous jobs landed across several CPU types, including AMD EPYC 7763, AMD EPYC 9V45, Intel Xeon Platinum 8573C and Intel Xeon 6973P-C. Direct fine-grained throughput ranking from this run is therefore inappropriate.

## Operational findings

### Eight-way fan-out is practical

GitHub accepted all eight standard-runner matrix jobs into active execution concurrently. This does not guarantee future scheduler placement or account-wide concurrency, but it proves an eight-way request can obtain full overlap under the observed conditions.

### Model transfer is already cheap relative to long experiments

The seven first-pass successful model downloads ranged from 13 to 34 seconds for roughly 1.9–5.2 GB. The corrected Qwen2.5-Omni retry took 53 seconds for 4.68 GB.

For planned multi-hour jobs, these transfers are a very small fraction of wall time. A seedbox/model library would still improve control, reproducibility, upstream independence and multi-model staging, but raw first-time Hugging Face transfer speed is not currently blocking long-duration workers.

### Startup overhead is negligible

All successful model servers became healthy within approximately 1.3–4.0 seconds after the model was present locally.

### Memory

Even the heavyweight lanes fit the standard runner:

- Qwen2.5-Omni-7B: ~7.43 GiB RSS at the 2K smoke context.
- LFM2.5-8B-A1B: ~8.58 GiB RSS at the 2K smoke context.

This leaves useful headroom inside the roughly 16 GiB runner class, although multi-model residency and larger contexts must be budgeted separately.

### Pin validation caught a real registry error

The first Qwen2.5-Omni job failed closed because the stored SHA-256 did not match the actual ggml-org Q4_K_M object. The authoritative current file hash was corrected in `config/candidates.json`, and the targeted retry passed.

This validates the decision to require checksum verification before model startup.

## Initial interpretation

For long-running workers, raw decode throughput should not be used as an exclusion gate. Even Ministral's short smoke observation of ~3.5 tok/s implies substantial output over multi-hour jobs. Models should instead be evaluated by useful-survivor yield, novelty retention, judge quality and improvement per runner-hour.

The next controlled comparisons should hold prompt/task and host methodology as constant as practical and run long enough to reduce short-response timing noise.
